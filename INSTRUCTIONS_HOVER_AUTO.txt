================================================================================
  АВТОНОМНЕ ЗАВИСАННЯ FPV ДРОНА — ІНСТРУКЦІЯ
================================================================================

Дата: квітень 2026
Скрипт: drone_hover_auto.py
Апарат: Meteor 75 Pro (або інший мікро-FPV без GPS/барометра)
Камера: forward-facing, відео через HDMI capture card
Телеметрія: Pitch/Roll з пульта → USB Serial → ПК

  1. ЗАГАЛЬНИЙ ОПИС
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Скрипт drone_hover_auto.py реалізує closed-loop control для
  автоматичного зависання FPV дрона на 5 секунд із подальшою посадкою.

  Дрон НЕ має власних "мізків" — ВСЯ логіка виконується на ПК:
    • Відео з камери → HDMI capture card → ПК (cv2.VideoCapture)
    • Гіроскоп-дані (Pitch/Roll) → пульт → USB Serial → ПК
    • Optical Flow + PID → обчислення корекцій
    • Команди RC каналів → пульт → дрон

  Пайплайн (Control Loop, 30 Hz):

    ┌─────────────┐     ┌─────────────┐
    │ HDMI Capture │     │ USB Serial  │
    │ (відео)      │     │ (гіроскоп)  │
    └──────┬───────┘     └──────┬──────┘
           │                    │
           ▼                    ▼
    ┌─────────────────────────────────┐
    │  Optical Flow (Lucas-Kanade)    │
    │  + Компенсація обертання        │
    │    (gyro pitch/roll)            │
    └──────────────┬──────────────────┘
                   │
                   ▼
    ┌─────────────────────────────────┐
    │  PID Controllers                │
    │  (Throttle, Roll, Pitch)        │
    └──────────────┬──────────────────┘
                   │
                   ▼
    ┌─────────────────────────────────┐
    │  State Machine                  │
    │  HOVER (5s) → LAND → DONE      │
    └──────────────┬──────────────────┘
                   │
                   ▼
    ┌─────────────────────────────────┐
    │  Вивід RC команд (mock/CRSF)   │
    └─────────────────────────────────┘

  3. АПАРАТНЕ ПІДКЛЮЧЕННЯ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Компоненти:

    A. HDMI Capture Card
       Підключається до відеоприймача (Skyzone Cobra X / аналог)
       через HDMI і працює як USB-камера на ПК.

       Перевірка:
         python -c "import cv2; cap=cv2.VideoCapture(0); print(cap.read()[0])"
       Якщо True — все ок. Якщо ні — спробуй індекс 1, 2, ...

    B. USB Serial (телеметрія гіроскопа)
       Пульт передає Pitch/Roll через COM-порт.
       Формат даних (один рядок на оновлення):

         Варіант 1 (простий):   P:12.5,R:-3.2
         Варіант 2 (JSON):      {"pitch": 12.5, "roll": -3.2}

       Перевірка порту на macOS:
         ls /dev/cu.usb*
       Або:
         python -m serial.tools.list_ports

    C. Відправка команд на пульт
       Поточна версія — mock (print у консоль).
       Для реального керування замінити send_command() на:
         • CRSFSender з rc_crsf_serial.py (USB-C → пульт GX12)
         • Або PPM через аудіовихід (rc_ppm_audio.py)

  4. КОНФІГУРАЦІЯ (параметри у drone_hover_auto.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ┌───────────────────────┬────────────┬─────────────────────────────────────┐
  │ Параметр              │ Дефолт     │ Пояснення                           │
  ├───────────────────────┼────────────┼─────────────────────────────────────┤
  │ CAMERA_INDEX          │ 0          │ Індекс HDMI capture card            │
  │ FRAME_WIDTH           │ 640        │ Ширина кадру (px)                   │
  │ FRAME_HEIGHT          │ 480        │ Висота кадру (px)                   │
  │ SERIAL_PORT           │ /dev/cu..  │ COM-порт гіроскопа                  │
  │ SERIAL_BAUD           │ 115200     │ Швидкість serial                    │
  │ FOCAL_LENGTH_PX       │ 300        │ Фокусна відстань камери (px) *      │
  │ RC_THROTTLE_HOVER     │ 1450       │ Базовий газ для зависання (µs) **   │
  │ HOVER_DURATION_SEC    │ 5.0        │ Тривалість зависання (секунди)      │
  │ LAND_THROTTLE_STEP    │ 5          │ Зменшення газу при посадці (µs/цикл)│
  │ CONTROL_LOOP_HZ       │ 30         │ Частота control loop                │
  └───────────────────────┴────────────┴─────────────────────────────────────┘

  *  FOCAL_LENGTH_PX — наближення для FPV камери ~120° HFOV.
     Можна обчислити:  f = (width / 2) / tan(HFOV / 2)
     Приклад: 640/2 / tan(60°) ≈ 185.  Після калібрування — замінити.

  ** RC_THROTTLE_HOVER — КРИТИЧНО ВАЖЛИВИЙ параметр.
     Це значення Throttle (мікросекунди), при якому дрон "висить".
     Для Meteor 75 Pro зазвичай 1350–1500. Визначається експериментально.

  5. PID ТЮНІНГ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  У коді три PID-регулятори:

    PID_THROTTLE — корекція висоти (по вертикальному flow)
    PID_ROLL     — корекція бічного дрейфу (по горизонтальному flow)
    PID_PITCH    — корекція руху вперед/назад (по дивергенції flow)

  Рекомендована процедура тюнінгу:

    1. Почни з МАЛИХ значень:  kp = 0.1,  ki = 0,  kd = 0
    2. Збільшуй kp поки дрон не почне реагувати на дрейф
    3. Якщо осциляції — зменш kp, додай kd (починай з 0.05)
    4. ki додавай останнім (0.01–0.05) для компенсації постійних похибок

    ⚠️  ТЮНІНГ ПРОВОДИТИ НА ПРИВ'ЯЗЦІ!
        Прив'яжи дрон мотузкою до чогось, щоб він не вилетів
        при неправильних коефіцієнтах.

  Anti-windup: PID автоматично обмежує інтегральну складову,
  щоб уникнути "розмотки" при тривалій похибці.

  6. МАТЕМАТИКА — КОМПЕНСАЦІЯ ОБЕРТАННЯ OPTICAL FLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ПРОБЛЕМА:
    Камера дрона дивиться вперед. Коли дрон нахиляється (pitch/roll),
    ВСЯ картинка зсувається. Optical Flow "бачить" цей зсув і помилково
    вважає, що дрон переміщується в просторі.

  РІШЕННЯ:
    Використовуємо дані гіроскопа, щоб обчислити "уявний" рух
    від обертання камери і відняти його від виміряного потоку.

  ФОРМУЛИ (pinhole camera model, Trucco & Verri):

    Для пікселя з координатами (u, v):
      x = u − cx    (відхилення від головної точки)
      y = v − cy

    Кутові швидкості камери за один кадр (радіани):
      ω_x = delta_pitch   (обертання навколо горизонтальної осі)
      ω_z = delta_roll     (обертання навколо оптичної осі)
      ω_y = 0              (yaw невідомий з телеметрії)

    Обертальна складова потоку:
      flow_u_rot = (x·y / f) · ω_x  +  y · ω_z
      flow_v_rot = (f + y²/f) · ω_x  −  x · ω_z

    Трансляційний (чистий) потік:
      flow_u_trans = flow_u_measured − flow_u_rot
      flow_v_trans = flow_v_measured − flow_v_rot

  ІНТЕРПРЕТАЦІЯ (камера дивиться вперед):
    • flow_v_trans > 0  →  дрон опускається (потрібно більше throttle)
    • flow_u_trans > 0  →  дрон дрейфує вправо (потрібно roll вліво)
    • divergence > 0    →  дрон наближається до сцени (потрібно pitch назад)

  7. АРХІТЕКТУРА КОДУ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Клас / Функція              Потік         Опис
  ─────────────────────────────────────────────────────────────────────────
  ThreadedVideoCapture        daemon        Захоплення кадрів з камери.
                                            Зберігає лише останній кадр.

  GyroReader                  daemon        Читає Pitch/Roll з Serial.
                                            Thread-safe доступ через
                                            .pitch / .roll properties.

  OpticalFlowProcessor        main          Lucas-Kanade optical flow +
                                            компенсація обертання.
                                            Повертає: flow_x, flow_y,
                                            divergence, debug_frame.

  PIDController               main          Дискретний PID з anti-windup.
                                            Три інстанси для throttle,
                                            roll, pitch.

  send_command()              main          Mock — print RC каналів.
                                            Замінити на CRSF/PPM для
                                            реального залізу.

  main()                      main          Control loop 30 Hz.
                                            State machine: HOVER→LAND.
  ─────────────────────────────────────────────────────────────────────────

  Багатопоточність:
    main thread ← control loop (30 Hz)
    daemon #1   ← ThreadedVideoCapture (постійно оновлює self._frame)
    daemon #2   ← GyroReader (постійно оновлює self._pitch, self._roll)

    Потоки синхронізуються через threading.Lock. Control loop ніколи не
    блокується на I/O — завжди читає останні доступні дані.

  8. STATE MACHINE (СТЕЙТ-МАШИНА)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    ┌───────────┐   5 секунд    ┌──────────┐  throttle ≤ 1000  ┌────────┐
    │  HOVER    │──────────────►│  LAND    │──────────────────►│  DONE  │
    │           │               │          │                   │        │
    │ PID усіх  │               │ Throttle │                   │ Мотори │
    │ 3-х осей  │               │ ↓ плавно │                   │ вимкн. │
    └───────────┘               └──────────┘                   └────────┘

    HOVER:
      - Тривалість: HOVER_DURATION_SEC (5 с)
      - PID корекція по всіх 3 осях (throttle, roll, pitch)
      - Мета: утримати нульовий translational optical flow

    LAND:
      - Throttle зменшується на LAND_THROTTLE_STEP (5 µs) кожну ітерацію
      - Roll-корекція залишається активною (щоб не здути набік)
      - Pitch фіксований на середині (1500)
      - Завершення: коли throttle ≤ RC_MIN (1000)

    DONE:
      - Фінальна команда: throttle = 1000, все інше = 1500
      - Цикл зупиняється, ресурси звільняються

  9. ЗАПУСК
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. Активуй .venv:
       source .venv/bin/activate

  2. Встанови залежності (якщо ще не):
       pip install opencv-python numpy pyserial

  3. Відредагуй параметри у drone_hover_auto.py:
       • CAMERA_INDEX — індекс HDMI capture card
       • SERIAL_PORT  — COM-порт гіроскопа

  4. Запусти:
       python drone_hover_auto.py

  5. Натисни 'q' у вікні OpenCV для аварійної зупинки.

  10. ПЕРЕХІД ДО РЕАЛЬНОГО ЗАЛІЗУ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Крок 1: Калібрування камери
    Визначити FOCAL_LENGTH_PX точно через калібрувальну шахівницю OpenCV
    або обчислити з відомого HFOV:  f = (width/2) / tan(HFOV/2)

  Крок 2: Заміна send_command() на CRSFSender
    У drone_hover_auto.py замінити функцію send_command() на виклик:

      from rc_crsf_serial import CRSFSender
      sender = CRSFSender("/dev/cu.usbmodem14201")
      sender.open()
      # У control loop:
      sender.send_channels([roll, pitch, throttle, yaw])

  Крок 3: Телеметрія гіроскопа
    Налаштувати прошивку пульта (або окремий ESP32) на передачу
    Pitch/Roll через USB Serial у форматі "P:<val>,R:<val>\n"

  Крок 4: Тест на прив'язці
    ⚠️  ЗАВЖДИ починати з тесту на прив'язці!
    Мотузка ~50 см, прикріплена до нерухомого об'єкта.

  Крок 5: PID тюнінг (див. розділ 5)

  Крок 6: Вільний політ
    Тільки після успішного тесту на прив'язці. У відкритому просторі.
    Тримай пульт у руках для ручного перехоплення (failsafe).

  11. ВІДОМІ ОБМЕЖЕННЯ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  • Yaw (рискання) НЕ компенсується — телеметрія не має yaw-даних.
    При повороті дрона навколо вертикальної осі optical flow
    може давати хибні показники.

  • Optical Flow працює найкраще при текстурованій сцені.
    Однотонна підлога / стеля = мало фіч = погана стабілізація.

  • Latency: HDMI capture + обробка = ~50–100 мс.
    Це прийнятно для hover, але може бути замало для агресивного
    маневрування. Для зменшення затримки — знизити роздільність.

  • Масштаб: optical flow дає переміщення в пікселях, а не в метрах.
    PID працює з "піксельними" похибками. Це нормально для
    стабілізації, але не дає абсолютного позиціонування.

  • Висота оцінюється побічно (через vertical flow).
    Без далекоміра / ToF-сенсора абсолютна висота невідома.
